# Post-Trade Analytics Pipeline (Snowflake + dbt)

![dbt CI](https://github.com/phikamihlali/post-trade-analytics/actions/workflows/dbt_ci.yml/badge.svg)

A medallion-architecture pipeline for post-trade data. Raw executions and market benchmarks land in Bronze, are cleaned and enriched in Silver, and become a settlement ledger and an exceptions table in Gold.

> **All data is synthetic.** It is generated by `scripts/generate_data.py`, with known problems planted so the pipeline can be tested against an answer key.

## Architecture

| Layer | What it does | Where |
|---|---|---|
| Bronze | Raw landing, all VARCHAR so nothing is rejected on load | `setup/`, `models/staging/sources.yml` |
| Silver | Typing, cleaning, validity and duplicate flags, TCA slippage vs VWAP, T+2 settlement date (weekends skipped) | `models/staging/`, `models/intermediate/` |
| Gold | `fct_clearing_ledger` (netted by date, counterparty, currency) and `exceptions_trades` | `models/marts/` |

Tests live in `tests/` and in the `schema.yml` files.

## Design decisions

- **Follow data quality checking steps and preparations before getting hands on the project.** 
- **Keep the first copy of a duplicate** in the ledger, so a real trade is not dropped.
- **`TRY_CAST` on raw data**, so one bad value becomes NULL instead of failing the model.
- **Gold is a table, not incremental.** An incremental merge overwrote totals with partial sums when late trades arrived.
- **dbt runs as a limited role (`DBT_ROLE`) with key-pair login**, not as ACCOUNTADMIN with a password.
- **Planted problems are `warn` tests**, so the build stays green while the problems stay visible.

The full list, with what I rejected and why, is in `docs/decisions.md`.

## Testing and CI

- 17 dbt tests: keys, accepted values, a ledger-to-Silver reconciliation, and no weekend settlement dates.
- Five tests are set to `warn` because they catch the planted problems (null timestamp, price, counterparty, duplicate ID, currency/venue mismatch).
- GitHub Actions runs `dbt parse` with a dummy profile on every push. It checks the project structure but does not connect to Snowflake. The tests were run against Snowflake in my dev environment.

## Known limitations

- **Fat-finger quantities are not detected.** Sizes come from a fixed list and 10,000 is already a normal size, so value rules cannot flag them. An early rule-based check caught 86 of 100 planted outliers. Catching the rest needs order-level context.
- **One settlement date.** The data covers a single trading day, so the ledger has one date.
- No FX conversion, so cash is never summed across currencies.
- No market-holiday calendar, and T+2 is a simplification (US equities moved to T+1 in 2024).
- No dashboard yet.

## How to run

1. `python scripts/generate_data.py` creates the CSVs (the answer-key files are never loaded).
2. Run `setup/01_bronze_setup.sql` in Snowflake.
3. Upload `bronze_trades.csv` and `bronze_market_feed.csv` to `trade_stage`.
4. Run `setup/02_bronze_load.sql`.
5. Create a dbt profile for the `post_trade_project` profile name, then run `dbt deps`, `dbt build` and `dbt test`.
